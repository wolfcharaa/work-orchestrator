# Очереди, барьеры и расширение допуска

[English](../en/work-queues.md) · [README](../../README.md)

`WorkQueue` отвечает не за выполнение задачи, а за **admission (допуск)**:
когда следующий `WorkEnvelope` разрешено передать primary worker. Очередь живёт
только в root-процессе, поэтому в ней можно хранить локальное состояние root, но
она должна быть конечной и не должна выполнять бизнес-обработку данных задачи.

## Как выбрать очередь

| Требование | Используйте | Что гарантируется |
| --- | --- | --- |
| Все задачи независимы | `OrderedWorkQueue` | Выдача в заданном порядке без ожидания завершения предыдущей |
| Есть последовательные стадии | `GroupedWorkQueue` | Следующая строгая группа не откроется, пока не завершена текущая |
| Задачи — найденные файлы | `FileWorkQueue::discover()` | Root один раз строит canonical file manifest и обычную ordered queue |
| Файлам нужны стадии и независимые fillers | `FileWorkQueue::discoverGrouped()` | Приоритет файла преобразуется в строгие группы и независимый запас |
| Нужен иной протокол допуска | собственный `WorkQueue` | Приложение полностью владеет состоянием, разрешениями и сигналом готовности |

Если нужен только порядок выдачи, не используйте barrier: `OrderedWorkQueue`
может выдать второй item до завершения первого и тем самым не оставляет worker
без работы.

## Strict-барьер

Strict-группа — набор работ одной стадии. Все её элементы можно выполнять
параллельно, но следующая группа остаётся закрытой до завершения **каждого**
элемента текущей:

```php
$queue = new GroupedWorkQueue([
    [$loadRegions, $loadTypes], // stage 0
    [$loadAddresses],           // stage 1 depends on all of stage 0
]);
```

При трёх workers последовательность допуска выглядит так:

| Момент | Worker 1 | Worker 2 | Worker 3 | Состояние stage 1 |
| --- | --- | --- | --- | --- |
| начало | `loadRegions` | `loadTypes` | ждёт | закрыта |
| одна задача stage 0 готова | готов | всё ещё работает | ждёт | закрыта |
| вся stage 0 готова | готов | готов | — | `loadAddresses` разрешена |

Barrier нужен для реальной зависимости данных, например когда addresses можно
читать только после полной загрузки dictionaries. Он не предназначен для
обычного «сначала добавили в массив» — это уже даёт ordered queue.

## Opportunistic work: полезная загрузка свободных workers

Opportunistic-задача не относится к последовательной стадии и не открывает
следующий барьер. Пока последняя долгая строгая задача ещё выполняется, такая
независимая работа может занять освободившийся worker:

```php
$queue = new GroupedWorkQueue(
    groups: [[$largeA, $largeB], [$dependent]],
    opportunistic: [$smallIndependentDictionary],
);
```

Используйте эту lane, только если задача:

- не читает частично готовую строгую стадию;
- не является условием открытия следующей стадии;
- безопасно выполняется в любое время текущего run.

Управление выполняется двумя списками конструктора: `groups` определяет строгие
барьеры, `opportunistic` — независимый запас. Отдельного динамического
приоритета во время run нет. Если эти условия сложно доказать, оставьте item в
явной строгой группе.

## Файловый адаптер

`FileWorkQueue` — фабрика готовых очередей, а не отдельный runtime. Root один раз
находит файлы, получает canonical path и размер, затем создаёт
`WorkEnvelope<FileEntry>`:

```php
$queue = FileWorkQueue::discover(
    ['/data/incoming', '/data/manual.ndjson'],
    patterns: ['*.ndjson', '/^part-\d+\.json$/i'],
    order: FileOrder::largestFirst(),
);
```

Patterns фильтруют содержимое каталогов; явно переданный файл включается всегда.
Доступны `pathAscending()`, `largestFirst()`, `smallestFirst()` и
`custom(Closure)`. Canonical path становится `WorkId`; дубликаты отклоняются до
старта workers.

Для grouped discovery `FilePriority::fromBasenamePatterns()` сопоставляет
basename и возвращает `AdmissionPriority::strict($number)` либо
`AdmissionPriority::opportunistic()`. Меньшие strict-числа открываются раньше.
Payload всё равно остаётся обычным `FileEntry`; parse/write принадлежат
стратегии.

## Протокол собственной `WorkQueue`

Собственная очередь уместна, когда admission зависит от квоты, внешнего окна
или специфического состояния root, которое нельзя выразить группами.
Публичный контракт состоит из трёх методов:

1. `count()` возвращает неизменное общее число работ и должен быть больше нуля.
2. `acquire()` возвращает ровно один из вариантов:
   - `Granted(TaskLease)` — работа выдана;
   - `Blocked(Future)` — сейчас выдавать нельзя; future завершится при изменении
     состояния, после чего root снова вызовет `acquire()`;
   - `Exhausted` — новых работ больше никогда не будет.
3. `complete($lease, $outcome)` принимает **тот же объект** `TaskLease` один раз,
   снимает состояние «выполняется» и при необходимости будит ожидающих callers.

Каждый `WorkId` должен быть уникальным, `TaskLease::position` — уникальной
позицией результата, а lease ID — уникальным внутри очереди. Не возвращайте
`Blocked` с уже завершённым future: это создаст цикл без ожидания. Не считайте
`TaskOutcome` обязательно успешным — завершение допуска и бизнес-успех разные
состояния.

`AbstractTaskQueue` помечен `@internal`: наследоваться от него нельзя. Полный
публичный пример [`WindowedWorkQueue`](../../examples/CustomQueue/WindowedWorkQueue.php)
сам проверяет duplicate IDs, exact lease identity, повторное завершение и
обновление readiness-сигнала. Он ограничивает число выданных, но ещё не завершённых
root-задач:

```bash
composer example:custom-queue
```

Ожидаемый вывод:

```text
customer:42 => 42
customer:77 => 77
run => succeeded
```

При `primaryWorkers(2)` и `maxInFlight: 1` второй scheduler lane получает
`Blocked`; завершение первого lease будит её и разрешает вторую задачу. Пример
показывает механику расширения, но application-specific queue всё равно должна
иметь тесты на поддельное/повторное разрешение, отмену ожидания и исчерпание.

## Что расширять, а что нет

- Реализуйте `WorkQueue`, если меняется именно политика допуска.
- Реализуйте `Strategy`, если меняется обработка уже выданных данных задачи.
- Используйте managed tasks, если одна выданная работа делится на ограниченные
  подзадачи; не превращайте root queue в динамическое дерево.
- Не используйте типы из `Internal` и `File\Internal`: они не являются
  совместимыми точками расширения.
